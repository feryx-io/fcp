## What is next (proposed 2026-09-16)

**Tenant trunks** — chosen after E911 block 2 closed. The trunks `/v1/trunks`
manages do not carry calls: outbound routing is built only from each node's
TOML `[[trunks]]`, and nothing outside the API and the storage layer reads a
database trunk's digits, codecs, caller ID, CPS, SRTP, DTMF, session timer,
outbound proxy, trunk group or header rules. Block 2 had to work around it
(`docs/E911_BLOCK_2.md` §12.1: `emergency_capable` on a database trunk decides
nothing). Design in `docs/TENANT_TRUNKS.md` (v0.25.182): one trunk model,
selection over the tenant's trunks then the platform's, the trunk's own
behaviour applied to the calls it carries, inbound tenancy from the trunk,
one node registering a registering trunk, and `emergency_capable` made real;
six phases, nine open questions with recommendations, every recommendation taken. Phase 1 done (v0.25.185): one trunk model — `fcp_core::Trunk` is what a tenant manages, what a node's `[[trunks]]` parses into and what the call path holds (`TrunkConfig` an alias of it, migration 072 giving the stored trunk the columns it lacked), identified by `TrunkId` rather than by name so two tenants' `carrier-a` never share health or capacity; no routing change yet. Phase 2 done (v0.25.186): tenant trunks route — every routing node holds a `TrunkSet` of its own `[[trunks]]` and every tenant's, read at startup, on the `system.config_changed` the trunks API now publishes, and on a backstop tick (`[trunk_routing] refresh_secs`); selection takes the caller's tenant and is that tenant's trunks then the platform's unless the tenant refuses them (`tenants.platform_trunk_fallback`); a node with no `[[trunks]]` of its own still routes; health probes follow the set; the record names which trunk carried the call (`cdrs.trunk_id`); and the floor routes two tenants to two carriers on one node. It found that on a node with a database an outbound call to an E.164 that is nobody's DID never reached a trunk at all (only the no-storage path asked the route provider), and that `platform_trunk_fallback` read back `true` whatever was stored; both fixed in the phase. Phase 3 is split in two: 3a done (v0.25.187) — the route carries the trunk itself (`OutboundRoute.trunk`), and the leg it carries presents the trunk's identity (`caller_id_override`, `from_domain`, `P-Asserted-Identity`), asks for its session timer (RFC 4028, with the 90-second floor), is offered RFC 2833 only if the trunk takes it, and goes to the trunk's `outbound_proxy` when it has one; asserted on the wire by `fcp-call-manager/tests/trunks.rs`. 3b is three PRs: 3b-1 done (v0.25.188) — a trunk whose `srtp` is `preferred` or `required` is offered `RTP/SAVP` with the key this node sends with, a carrier answering a `required` trunk in the clear gets a BYE and the caller a `488`, a `required` trunk on media this node does not anchor is refused rather than sent in the clear, and the media backend stopped arming the B-leg with a freshly generated local key when an answer carried `a=crypto` (RFC 4568 §5.1.2: that key must be the one this node advertised, or the carrier hears noise); 3b-2 is header rules and per-trunk STIR/SHAKEN signing (the HMR engine and its rule set are the SBC binary's today, and the rules act on a request this node generates, so the UAC needs a last look at it); 3b-3 is DTMF converted rather than only offered.
