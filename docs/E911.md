# Emergency Calling (E911)

FCP treats emergency calls as a first-class call type. When a caller dials an
emergency number, the B2BUA detects it before any other processing, resolves
the caller's **dispatchable location**, sends the call out with that
location's **callback number** as caller ID, records the call, and publishes
an event that on-site notification hooks into.

This document describes what exists: the first E911 block (2026-09-02),
with ELIN-style location delivery, a pluggable address validator with
manual validation, and emergency-capable trunks; and block 2's first phase
(2026-09-15, `docs/E911_BLOCK_2.md`), which makes every way a call can be
placed an emergency path and completes each call's record when it ends; and
its second, location by value; its third, locating a device by where it
is; its fourth, validation; its fifth, on-site notification delivered by the
platform; and its sixth, the admin UI (see "Location by value", "Where the
device is", "Address validation", "On-site notification" and "In the admin
UI").

## Regulatory background (US)

- **Kari's Law**: 911 must be dialable directly (no prefix), and someone on
  site must be notified when an emergency call is placed.
- **RAY BAUM's Act**: the call must carry a *dispatchable location* — the
  civic address plus enough detail (floor, suite) to find the caller.

FCP honours both by design: direct and prefixed dialing both work, every
emergency call publishes a `call.emergency` event carrying the tenant's
notification contacts, and the location precedence below is applied on every
call.

## Data model

| Where | Field | Purpose |
|---|---|---|
| Site location (`/v1/locations`) | address fields, `floor`, `building` | The civic address for everyone assigned to the site |
| Site location | `e911_callback_number` | The ELIN the carrier maps to this address; becomes caller ID |
| Site location | `civic`, `latitude`, `longitude` | The street as RFC 5139 civic elements, and the point on the map, for the location by value |
| Site location | `e911_validated_at`, `e911_validated_by`, `e911_validation_reference` | What a validator said about the address, cleared when the address is edited |
| Device (`/v1/devices`) | `e911_override` | A full address for one physical phone that differs from its site |
| Device / User | `location_id` | Which site the device / user sits at |
| Phone number (`/v1/phone-numbers`) | `e911_address`, `e911_callback` | Address registered for a DID, with its `validated` flag; the address takes civic elements too, as does a device's `e911_override` |
| Trunk (`[[trunks]]` TOML on each call manager) | `emergency_capable` | Trunks tried first for emergency calls, in priority order |
| Trunk (`[[trunks]]`) | `emergency_location` | How the location travels on it: `["elin"]` (default), `["pidf_lo"]`, or both |
| Trunk (`/v1/trunks`) | `emergency_capable` | Stored, but does not route calls: database trunks only admit inbound calls until tenant trunk routing exists (see "Trunks" below) |
| Tenant | emergency config (`/v1/emergency/config`) | Emergency / test numbers, dial prefixes, notification contacts |

### Location precedence

The resolver (`fcp_core::e911::resolve_dispatchable_location`) picks the
first complete source:

1. The device's `e911_override`.
2. A location the device sent with the call, from a device the tenant
   trusts to send one.
3. The site of the network the caller's address is on, for devices that
   network places.
4. The device's site, if it has street, city, state, and postal code.
5. The user's site, same rule.
6. The user's declared location, while it has not expired.
7. The E911 address on the user's phone number.

Floor and building on a site become the second address line when the site
has none. A site without a complete address is skipped, never dispatched.

The **callback number** is chosen independently: the device site's ELIN,
then the user site's ELIN, then the number's `e911_callback`, then the
number itself. A device override therefore still goes out with its site's
ELIN.

## Call flow

Every way a call is placed takes the same path (`fcp_sip::emergency`):
an INVITE from a phone, a flow's `Dial` node, and a browser's call through
the WebRTC gateway (see "From a browser").

1. `INVITE` arrives. The dialed number (To header user part) is classified
   against the tenant's config: `911` (and `9911` with the default prefix)
   is a **live** emergency, `933` is a **test** call. Tenants can change the
   numbers (`112`, `999`, …) and prefixes.
2. **Balance admission is skipped.** An emergency call is never answered
   with 402.
3. The location is resolved for the caller's user. The call carries the
   result (`Call.emergency`).
4. The `call.emergency` event is published and an `emergency_calls` row is
   written (both best-effort, never blocking the call).
5. Routing skips extension and DID lookup entirely: an extension named
   `911` cannot capture the call. Routes come from
   `OutboundRouteProvider::resolve_emergency_ordered`: every eligible
   `emergency_capable` trunk first (by priority), then the normal LCR
   choice. The routes are tried one at a time, in that order, and never
   two at once, so no second carrier gets the call while the first might
   answer. A route that refuses or does not answer within
   `[b2bua.forking] timeout` gives way to the next. With no upstream trunk
   at all the call fails with 503 and an error-level log line.
6. The outbound INVITE uses the callback number as the From user, adds
   `P-Asserted-Identity: <sip:<callback>@<host>>`, and `Priority: emergency`.
7. When the call ends, its record is completed with the trunk that
   answered (or the last one tried), the outcome (`answered`, `busy`,
   `no_answer`, `failed`, `cancelled`), the final SIP status, when it was
   answered and ended, and how the location travelled (`delivery`: `elin`
   when there was a callback number). `call.emergency_completed` is
   published with the same facts.

A flow's `Dial` node whose destination is an emergency number for the
tenant does the same: it classifies the number and locates the flow's
caller, marks the call, writes the record and publishes the event. It
then dials each emergency route in turn with the callback number as the
caller, moving on after anything but an answer or a cancel. With no route,
it takes the node's `on_error` branch.

A multipart INVITE body is read for its SDP part. A device that sends its
location with the SDP (RFC 6442) no longer breaks the call's media; the
location part itself is used from block 2's phase 3.

### From a browser

The WebRTC gateway places an emergency call only for a named tenant user
and only through a call manager (`docs/WEBRTC.md`, "Emergency numbers").
It refuses one with no caller (403) or no `[sip] outbound_proxy` (503),
with a reason the browser can show. It sends the caller as
`X-FCP-Caller-Tenant` and `X-FCP-Caller-User`.

The call manager believes those headers only from the addresses and CIDR
ranges in `[e911] trusted_edges`:

```toml
[e911]
trusted_edges = ["10.0.0.7", "10.1.0.0/24"]
```

From a trusted edge, the named user is the call's caller: their tenant,
their location, their name on the record. A trusted edge's INVITE is
admitted like a trunk's. From anyone else the headers are ignored (with a
warning) and never forwarded.

### Trunks

Outbound routing, emergency routing included, uses each call manager's
`[[trunks]]`. A trunk marked `emergency_capable` in the admin API
(`/v1/trunks`) is stored but routes nothing until tenant trunk routing
exists; that is its own project (`docs/E911_BLOCK_2.md` §12.1). Each call
manager reports what it will use at `GET /emergency/trunks` on its HTTP
port: its emergency-capable trunks in the order it tries them, each
enabled and healthy or not, and whether any is routable. It logs a warning
at startup when it has no trunks, or none that is emergency-capable.

When no location can be resolved the call still goes out (with the caller's
own identity) and the event, record, and a warning log all flag the gap.
`require_dispatchable_location` in the tenant config makes that gap
prominent in the readiness report; it never blocks the call.

## Location by value

A trunk that takes the location in the call — an NG911 provider — says so:

```toml
[[trunks]]
name = "ng911"
emergency_capable = true
emergency_location = ["elin", "pidf_lo"]   # default ["elin"]
```

On such a trunk the emergency INVITE carries (RFC 6442):

- a `multipart/mixed` body: the SDP, and a PIDF-LO
  (`application/pidf+xml`, RFC 4119 as RFC 5491 profiles it) named by a
  `Content-ID`;
- `Geolocation: <cid:…>` naming that part, and `Geolocation-Routing: yes`;
- the callback number as caller, `P-Asserted-Identity` and `Priority:
  emergency`, as on every emergency call.

The PIDF-LO has one `dm:device` whose entity is the callback number, a
`gp:geopriv` with the civic address, and, when the site has latitude and
longitude, a second `gp:geopriv` with a `gml:Point`. Retransmission is
allowed, and the method is `Manual` for a provisioned address.

The civic address comes from the location's RFC 5139 elements:

| Element | Field | Element | Field |
|---|---|---|---|
| `country` | `country` | `HNO` / `HNS` | `civic.house_number` / `house_number_suffix` |
| `A1` | `state` | `LOC` | `civic.additional` (or a second address line) |
| `A3` | `city` | `FLR` | the site's `floor` / `civic.floor` |
| `PRD` / `POD` | `civic.street_predirection` / `street_postdirection` | `NAM` | `civic.name`, else the site's name |
| `RD` | `civic.street_name` | `PC` | `postal_code` |
| `STS` | `civic.street_suffix` | `BLD` / `UNIT` / `ROOM` | the site's `building` / `civic.unit` / `civic.room` |

A site takes `civic` as an object on `/v1/locations`. A phone number's
`e911_address` and a device's `e911_override` take the same fields beside
their lines. An address whose street is not structured (no `street_name`
and `house_number`) is still sent, with its street line as `RD`, and the
record's `location_structured` is `false`. Validators that fill the
elements are block 2's phase 4.

When the trunk refuses the location — a `Geolocation-Error`, or 424 Bad
Location Information — the error goes on the record (`geolocation_error`).
A trunk that also takes `elin` is tried again with the callback number
alone; a trunk that takes only `pidf_lo` gives way to the next emergency
route. The record's `delivery` says how the location went on the
attempt that ended the call: `elin`, `pidf_lo` or `elin+pidf_lo`.

A flow's `Dial` node sends the same INVITE. An INVITE the call manager
sends over a device's existing connection (RFC 5626) now carries the same
extra headers as any other.

## Where the device is

A desk phone stays where it was installed. A softphone, a mobile app or a
browser does not, so the platform places it by the address it is seen at
(`docs/E911_BLOCK_2.md` §6).

### The address a call comes from

- **Registrations** keep the address they came from, so a device that has
  registered is placed even when its INVITE arrives through something else.
- **The INVITE's own source** is used when the call comes straight from the
  caller's device.
- **A trusted edge** — an SBC in front of phones, the WebRTC gateway in
  front of browsers — says where its client is in `X-FCP-Client-Address`.
  A call manager believes that header only from the addresses in `[e911]
  trusted_edges`, and never forwards it.

An edge sets `[e911] vouch_client_address = true` (the SBC's is under
`[core.e911]`) to add the header to the calls it passes on. The WebRTC
gateway always names the browser it saw; behind a load balancer, list the
balancer in the gateway's `[http] trusted_proxies` so `X-Forwarded-For` is
believed.

### Networks

A tenant maps its ranges to sites at `/v1/emergency/networks`:

```json
{ "cidr": "10.1.2.0/24", "location_id": "loc-…", "name": "Troy floor 2",
  "applies_to": "nomadic", "priority": 0 }
```

The most specific range wins, then the lowest `priority`. `applies_to` is
`nomadic` — softphones, mobile and browser clients, the default — or `all`,
which places desk phones too. A single address (`10.9.9.9`) is taken as a
network of one.

### A device's own location

An NG911-aware device can send its location with the call (a PIDF-LO beside
the SDP, RFC 6442). It is used only from devices the tenant trusts: device
types listed in `trust_device_locations` on `/v1/emergency/config`, or a
single device with `e911_trust_location` set on `/v1/devices`. From any
other device the claim is ignored and the provisioned location stands.

### Declared locations

A user who is on no mapped network says where they are:

| Method | Path | Purpose |
|---|---|---|
| GET | `/v1/me/location` | What I last said, with its age and expiry |
| PUT | `/v1/me/location` | Say where I am: an address, validated like any other (422 with the issues when it fails) |
| DELETE | `/v1/me/location` | I am no longer there |

A declaration stands for `declared_location_ttl_secs` (a day by default,
per tenant) and then stops being used. The record of a call placed on one
carries its age.

The readiness report flags a user whose devices all move but whom nothing
places where they are, and counts them in `unplaced_nomadic`.

## Admin API

All under `/api/v1`, tenant-scoped, admin role required.

| Method | Path | Purpose |
|---|---|---|
| GET / PUT | `/emergency/config` | Numbers, test numbers, dial prefixes, `notify_contacts`, `require_dispatchable_location`. GET shows defaults with `configured: false` until saved |
| GET | `/emergency/readiness` | Every enabled user with the location that would be dispatched today, its source and callback number, whether their devices move, and the issues that keep the user from being *ready* (no location, no callback, address not validated, nothing placing a device that moves) |
| GET / POST | `/emergency/networks` | The tenant's networks and the sites they are at |
| GET / PATCH / DELETE | `/emergency/networks/:id` | One network |
| GET | `/emergency/calls?limit=` | Audit trail, newest first: placement (caller, dialed number, kind, callback number, location), then once the call ends `outcome`, `sip_status`, `trunk_name`, `answered_at`, `ended_at`, `duration_secs` and `delivery` |
| POST | `/emergency/validate-address` | Run the validator on an address body without storing it |
| POST | `/phone-numbers/:id/e911/validate` | Validate the number's E911 address; on success it is normalised and marked `validated` with a timestamp (200), otherwise 422 with the issues |
| POST | `/locations/:id/e911/validate` | The same for a site: the normalised street, city, state and civic elements are written back and the site is marked validated (400 when the site has no dispatchable address) |
| POST | `/devices/:id/e911/validate` | The same for a device's `e911_override` (400 when it has none) |

### Address validation

Every address a call can be dispatched to is validated on the same three
routes above, or checked without being stored on
`/emergency/validate-address`. An address that passes is **normalised**
(whitespace collapsed, codes upper-cased, the street split into RFC 5139
elements) and marked `validated`, `validated_at` and `validated_by` — with
`provider_reference` when the validator gave one. One that fails answers
422 with `issues`.

- **Only a validator marks an address.** An address sent to the API with
  `"validated": true` arrives unvalidated; nothing but a validation route
  sets the mark.
- **Editing clears it.** Change any part of a site's address, a device's
  `e911_override` or a number's `e911_address` and the mark goes; send the
  same address again and it stands. The readiness report then says the
  address has not been validated until it is checked again.
- **Notes are not issues.** `notes` say what the validator could not do on
  an address that is otherwise good — "no street suffix could be read from
  …" — without making it invalid.

`fcp_core::e911::E911AddressValidator` is the extension point, and
`[e911.validator]` in `fcp-admin` chooses the one this deployment uses:

| Provider | What it does |
|---|---|
| `basic` (default) | Completeness (house number, city, two-letter state, ZIP or ZIP+4 for US) and structure, with no external call: it splits `1455A N Market Street SW` into `HNO 1455`, `HNS A`, `PRD N`, `RD Market`, `STS St`, `POD SW`, and reads a second line such as `Suite 300` or `4th Floor` into `UNIT` / `FLR` |
| `http` | Posts the tidied, structured address to a service that can answer against an MSAG-grade database — the contract a thin adapter for any such provider implements |

```toml
[e911.validator]
provider = "http"
name = "acme-msag"                      # what validated addresses are marked by
url = "https://validate.example.net/e911"
token = "enc:v1:…"                      # or token_file = "/run/secrets/e911-validator"
timeout_secs = 5
```

The request is `{"address": {…lines and civic elements…}}` with the token as
a bearer, and the answer `{"valid": true, "normalized": {…}, "issues": [],
"notes": [], "provider_reference": "…"}`. A provider that cannot be reached
— a timeout, a 5xx, a body that does not parse — is an error, not an
invalid address: nothing is marked validated by a service that never
answered.

The bearer token may be a value sealed with the deployment's encryption at
rest. Seal it once with `POST /api/v1/system/encryption/seal`
(platform admin, `{"value": "…"}` → `{"sealed": "enc:v1:…"}`), put the
sealed string in the configuration file or the mounted `token_file`, and
`fcp-admin` opens it at startup (`docs/ENCRYPTION.md`).

## Events and notification

`call.emergency` (a `CallEvent::Emergency`) carries the call id, tenant,
caller, dialed number, kind (`live`/`test`), callback number, location
source and one-line summary, the client address that placed the caller,
trunk, and the tenant's `notify_contacts`.
It flows through the same paths as every call event: webhooks (subscribe to
`call.emergency`), the `/api/v1/events` WebSocket, and the events server.

`call.emergency_completed` (a `CallEvent::EmergencyCompleted`) follows
when the call ends: the call id, tenant, dialed number and kind, the
outcome and final SIP status, the trunk, the delivery method and the time
from answer to end.

`emergency.notification_failed` (a `CallEvent::EmergencyNotificationFailed`)
says that a contact could not be told, after every attempt: the contact,
how many attempts were made and the last error.

### On-site notification

Kari's Law requires that someone on site is told when an emergency call is
placed, and FCP delivers that itself (`docs/E911_BLOCK_2.md` §8). The
notifier runs in **fcp-events-server**, beside the webhook dispatcher, on
`call.emergency`.

**Contacts.** `/emergency/config` takes `contacts`, each typed:

| Kind | Target | Delivered by |
|---|---|---|
| `email` | an address | SMTP (`[notifications.smtp]`) |
| `sms` | an E.164 number | the SMS provider (`[notifications.sms]`) |
| `call` | an extension or SIP URI | a call that speaks the notice, placed by a call manager (`[notifications.call]`) |
| `webhook` | a webhook endpoint id | the dispatcher that is already there |

A contact may be written as plain text and is read by its shape — an `@` is
an email, a SIP URI or a short number a call, a longer number an SMS, a
UUID a webhook endpoint — so the free-text `notify_contacts` of block 1
keeps working and is migrated in place. The response carries both: typed
`contacts`, and `notify_contacts` as the plain strings it always was.

**The notice.** One text, rendered per channel: that an emergency call was
placed, by whom, the callback number, the location sent and its source,
where the caller was seen, the time — and, for a `933` call, `[TEST]` in
the subject and the first line, with "no emergency services were
contacted" at the end. The spoken form reads numbers digit by digit.

**Delivery.** Every contact is tried at once. Each attempt is a row in
`emergency_notifications` — the contact, the attempt number, the outcome,
the error, and the notice itself, so a retry needs nothing else. A failed
attempt is retried with a doubling delay until `max_attempts`, and never
later than `give_up_after_secs` from the call: a notice that arrives an
hour late tells nobody anything. The first delivery sets `notified` on the
call's record, and a contact that runs out of attempts raises
`emergency.notification_failed`.

```
GET /api/v1/emergency/calls/:call_id/notifications
```

lists every attempt for one call, oldest first.

**Readiness.** `/emergency/readiness` carries a `notifications` block: each
contact with what keeps it from being deliverable, when anything last
reached it, and when a test call's notice last did. A tenant with no
deliverable contact, or one that has never proved the chain with a `933`
call, is told so.

**Configuring the notifier** (`fcp-events-server`):

```toml
[notifications]
enabled = true
max_attempts = 5            # per contact, the first included
base_retry_delay_secs = 30  # doubles, up to max_retry_delay_secs
give_up_after_secs = 1800

[notifications.smtp]
host = "smtp.example.com"
port = 587
encryption = "starttls"     # or "tls", or "none" for a relay on this host
from = "fcp@example.com"
username = "fcp"
password = "enc:v1:…"       # sealed with encryption at rest

[notifications.sms]
url = "https://sms.example.net/send"   # POST {to, from, text, tenant_id, call_id, test}
token = "enc:v1:…"
from = "+15185550100"

[notifications.call]
call_manager_url = "http://fcp-call-manager:8080"
auth_token = "enc:v1:…"
from = "sip:alerts@pbx.example.com"
ring_timeout_secs = 30
repeat = 2                  # how often the notice is spoken once answered
```

Credentials may be sealed with the deployment's encryption at rest
(`POST /api/v1/system/encryption/seal`, `docs/ENCRYPTION.md`) and are
opened at startup. The call channel asks a call manager for
`POST /api/v1/emergency/notify-call`, which rings the extension, speaks the
notice through TTS and answers with what became of the call; only an
answered call counts as delivered, so the notifier's retries ring again.

## In the admin UI

**Operations → Emergency** (`/admin/emergency`) has four tabs:

| Tab | What it shows |
|---|---|
| Configuration | The emergency and test numbers, the dial prefixes, who is told (typed contacts, added and removed here), which device types are trusted to send their own location, and how long a declared location stands |
| Readiness | The summary tiles, whether anybody would be told (each contact with when anything last reached it and when a test last did), and every user with the location that would be dispatched today and what keeps them from being ready |
| Networks | The ranges that place a device where it is, each with its site, what it places (devices that move, or every device) and its priority |
| Calls | Every emergency call, and — behind **View** — what was sent with it and every attempt to tell somebody about it |

The fields the rest of the UI carries:

- **Locations** show the ELIN and whether the address has been validated, take
  the ELIN in the form, and validate the address from the row's menu.
- **Devices** show where the phone would be dispatched to (its site, or its own
  address and whether that is validated); the edit dialog takes the override and
  says whether a location the device sends is believed, and the row's menu
  validates the override. Clearing the address returns the phone to its site.
- **Phone numbers** say whether the registered E911 address has been validated,
  and validate it from the row's menu.
- **SIP trunks** carry `emergency_capable`, with the note that platform routing
  uses each node's own trunks until tenant trunks route.

## Configuration checklist for a tenant

1. Create sites with full addresses and an `e911_callback_number` each.
2. Assign users (and desk phones) to their sites; set `e911_override` on
   phones that sit somewhere else.
3. Register `e911_address` on DIDs used by remote users and validate them.
4. Flag at least one upstream `[[trunks]]` entry `emergency_capable` on
   every call manager, and check `GET /emergency/trunks` on each.
5. If browsers call out through the WebRTC gateway, set its `[sip]
   outbound_proxy` to a call manager, list the gateway in that call
   manager's `[e911] trusted_edges`, and pass `caller` on every
   `POST /v1/calls`. Do the same for an SBC in front of phones, with
   `[core.e911] vouch_client_address = true` on the SBC.
6. Map the networks your devices use to their sites
   (`/v1/emergency/networks`), and tell users who travel to declare a
   location (`/v1/me/location`).
7. Set `contacts` on `/emergency/config`, and configure the notifier's
   channels on the events server (`[notifications]`).
8. Check `/emergency/readiness` until every user is ready and the
   `notifications` block has no issues.
9. Place a `933` test call from a phone: confirm the callback number and
   address the carrier reads back, and that every contact receives the
   `[TEST]` notice.

## Not yet

Block 2 is complete (`docs/E911_BLOCK_2.md`). What it deliberately left out:
tenant trunks that route (so the API's `emergency_capable` decides which
trunk carries a call), named carrier adapters for address validation beyond
the HTTP contract, and `emergency_location` per trunk in the API rather than
each node's TOML.
