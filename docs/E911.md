# Emergency Calling (E911)

FCP treats emergency calls as a first-class call type. When a caller dials an
emergency number, the B2BUA detects it before any other processing, resolves
the caller's **dispatchable location**, sends the call out with that
location's **callback number** as caller ID, records the call, and publishes
an event that on-site notification hooks into.

This document describes the first E911 block (2026-09-02): ELIN-style
location delivery, a pluggable address validator with manual validation, and
emergency-capable trunks. Location by value (PIDF-LO / NG911) and
network-based location for softphones are planned follow-ups.

## Regulatory background (US)

- **Kari's Law**: 911 must be dialable directly (no prefix), and someone on
  site must be notified when an emergency call is placed.
- **RAY BAUM's Act**: the call must carry a *dispatchable location* — the
  civic address plus enough detail (floor, suite) to find the caller.

FCP honours both by design: direct and prefixed dialing both work, every
emergency call publishes a `call.emergency` event carrying the tenant's
notification contacts, and the location precedence below is applied on every
call.

## Data model

| Where | Field | Purpose |
|---|---|---|
| Site location (`/v1/locations`) | address fields, `floor`, `building` | The civic address for everyone assigned to the site |
| Site location | `e911_callback_number` | The ELIN the carrier maps to this address; becomes caller ID |
| Device (`/v1/devices`) | `e911_override` | A full address for one physical phone that differs from its site |
| Device / User | `location_id` | Which site the device / user sits at |
| Phone number (`/v1/phone-numbers`) | `e911_address`, `e911_callback` | Address registered for a DID, with its `validated` flag |
| Trunk (`/v1/trunks`, `[[trunks]]` TOML) | `emergency_capable` | Trunks tried first for emergency calls |
| Tenant | emergency config (`/v1/emergency/config`) | Emergency / test numbers, dial prefixes, notification contacts |

### Location precedence

The resolver (`fcp_core::e911::resolve_dispatchable_location`) picks the
first complete source:

1. The device's `e911_override`.
2. The device's site, if it has street, city, state, and postal code.
3. The user's site, same rule.
4. The E911 address on the user's phone number.

Floor and building on a site become the second address line when the site
has none. A site without a complete address is skipped, never dispatched.

The **callback number** is chosen independently: the device site's ELIN,
then the user site's ELIN, then the number's `e911_callback`, then the
number itself. A device override therefore still goes out with its site's
ELIN.

## Call flow

1. `INVITE` arrives. The dialed number (To header user part) is classified
   against the tenant's config: `911` (and `9911` with the default prefix)
   is a **live** emergency, `933` is a **test** call. Tenants can change the
   numbers (`112`, `999`, …) and prefixes.
2. **Balance admission is skipped.** An emergency call is never answered
   with 402.
3. The location is resolved for the caller's user. The call carries the
   result (`Call.emergency`).
4. The `call.emergency` event is published and an `emergency_calls` row is
   written (both best-effort, never blocking the call).
5. Routing skips extension and DID lookup entirely: an extension named
   `911` cannot capture the call. Routes come from
   `OutboundRouteProvider::resolve_emergency_ordered`: every eligible
   `emergency_capable` trunk first (by priority), then the normal LCR
   choice. With no upstream trunk at all the call fails with 503 and an
   error-level log line.
6. The outbound INVITE uses the callback number as the From user, adds
   `P-Asserted-Identity: <sip:<callback>@<host>>`, and `Priority: emergency`.

When no location can be resolved the call still goes out (with the caller's
own identity) and the event, record, and a warning log all flag the gap.
`require_dispatchable_location` in the tenant config makes that gap
prominent in the readiness report; it never blocks the call.

## Admin API

All under `/api/v1`, tenant-scoped, admin role required.

| Method | Path | Purpose |
|---|---|---|
| GET / PUT | `/emergency/config` | Numbers, test numbers, dial prefixes, `notify_contacts`, `require_dispatchable_location`. GET shows defaults with `configured: false` until saved |
| GET | `/emergency/readiness` | Every enabled user with the location that would be dispatched today, its source and callback number, and the issues that keep the user from being *ready* (no location, no callback, address not validated) |
| GET | `/emergency/calls?limit=` | Audit trail, newest first |
| POST | `/emergency/validate-address` | Run the validator on an address body without storing it |
| POST | `/phone-numbers/:id/e911/validate` | Validate the number's E911 address; on success it is normalised and marked `validated` with a timestamp (200), otherwise 422 with the issues |

### Address validation

`fcp_core::e911::E911AddressValidator` is the extension point. The built-in
`BasicAddressValidator` checks completeness (house number, city, two-letter
state, ZIP or ZIP+4 for US) and normalises whitespace and codes. A
provider-backed validator (Bandwidth, Intrado, SmartyStreets, …) plugs in
through `ApiState::with_e911_validator` without API changes.

## Events and notification

`call.emergency` (a `CallEvent::Emergency`) carries the call id, tenant,
caller, dialed number, kind (`live`/`test`), callback number, location
source and one-line summary, trunk, and the tenant's `notify_contacts`.
It flows through the same paths as every call event: webhooks (subscribe to
`call.emergency`), the `/api/v1/events` WebSocket, and the events server.
Delivering the on-site notification (email, SMS, a SIP MESSAGE to the front
desk) is the subscriber's job; `notified` on the audit record can be set
once that has happened.

## Configuration checklist for a tenant

1. Create sites with full addresses and an `e911_callback_number` each.
2. Assign users (and desk phones) to their sites; set `e911_override` on
   phones that sit somewhere else.
3. Register `e911_address` on DIDs used by remote users and validate them.
4. Flag at least one upstream trunk `emergency_capable`.
5. Set `notify_contacts` on `/emergency/config`.
6. Check `/emergency/readiness` until every user is ready.
7. Place a `933` test call from a phone and confirm the callback number and
   address the carrier reads back.
